# LAWZIC 트러블슈팅 기록

## 분석 취소 요청이 500 오류를 반환하고 `처리 중...` 상태에 멈춘 문제

### 1. 배경

기존 계약서 분석 API는 Spring Boot가 FastAPI의 LLM 분석 응답을 동기적으로 기다리는 방식이었다.
사용자가 긴 분석을 중간에 멈출 수 있도록 다음 구조로 변경했다.

```text
분석 시작 요청
→ Spring Boot 백그라운드 작업 생성
→ React가 분석 상태를 주기적으로 조회
→ 완료 시 결과 조회
→ 취소 요청 시 Future 중단 및 상태 변경
```

계약서 상태에는 취소 완료를 표현하기 위해 `CANCELLED` 값을 새로 추가했다.

### 2. 발생한 증상

- `분석 취소` 버튼을 누르면 HTTP 500 오류가 발생했다.
- 화면에는 `분석 취소 요청에 실패했습니다`가 표시됐다.
- 계약서 상태가 계속 `PROCESSING`으로 남았다.
- 백엔드와 프론트엔드를 재시작해도 동일한 문제가 반복됐다.
- 새 데이터베이스를 사용한 테스트에서는 취소가 정상 동작했다.

### 3. 처음 확인한 문제

취소 API가 실패했을 때 프론트엔드는 실제 취소 성공 여부를 확인하기 전에 상태 조회 루프를 종료하고 있었다.

```javascript
// 문제가 있던 흐름
++analysisRun.current;
await cancelAnalysis();
```

이 때문에 취소 요청이 실패하면 분석 완료나 실패 상태를 다시 확인할 방법이 없어 화면이 계속
`처리 중...`으로 남았다.

취소 API가 성공한 뒤에만 실행 번호를 변경하도록 순서를 수정했다.

```javascript
await cancelAnalysis();
++analysisRun.current;
```

이 변경으로 화면이 영구적으로 멈추는 문제는 방지했지만, 취소 API의 HTTP 500 오류 자체는 해결되지 않았다.

### 4. 근본 원인

`Contract.Status` enum에 다음 값을 새로 추가했다.

```java
public enum Status {
    UPLOADED, PROCESSING, COMPLETED, FAILED, CANCELLED
}
```

하지만 기존 H2 데이터베이스의 `contracts.status` 컬럼에는 테이블을 처음 생성할 당시의 enum 값만
허용하는 체크 제약조건이 남아 있었다.

```text
UPLOADED
PROCESSING
COMPLETED
FAILED
```

취소 처리에서 `CANCELLED`를 저장하면 기존 체크 제약조건을 위반해 DB 업데이트가 실패했다.
트랜잭션이 롤백되면서 상태는 `PROCESSING`으로 유지되고 API는 HTTP 500을 반환했다.

```text
분석 취소 요청
→ 실행 작업 interrupt
→ status = CANCELLED 저장 시도
→ 기존 H2 CHECK 제약조건 위반
→ 트랜잭션 롤백
→ status = PROCESSING 유지
→ HTTP 500
```

`spring.jpa.hibernate.ddl-auto=update`는 Java enum에 값이 추가됐다는 이유만으로 기존 컬럼의 체크
제약조건을 항상 원하는 형태로 갱신해 주지 않는다. 따라서 애플리케이션 코드와 기존 DB 스키마 사이에
차이가 발생했다.

새로운 인메모리 DB에서는 처음부터 `CANCELLED`가 포함된 제약조건이 생성됐기 때문에 테스트가
통과했다. 반면 실제 서비스가 사용하던 기존 파일 DB에서는 이전 제약조건이 유지되어 실패했다.

### 5. 최종 해결

별도 DB 마이그레이션 없이 기존 데이터베이스와 호환되도록 취소 후 상태를 새 값이 아닌
기존 `UPLOADED`로 되돌렸다.

```java
public enum Status {
    UPLOADED, PROCESSING, COMPLETED, FAILED
}

public void markCancelled() {
    status = Status.UPLOADED;
}
```

취소의 의미를 다음과 같이 정의했다.

```text
PROCESSING
→ 사용자가 분석 취소
→ 백그라운드 Future interrupt
→ 분석 결과 저장 차단
→ UPLOADED 상태로 복귀
→ 사용자가 다시 분석 가능
```

프론트 상태 조회도 `UPLOADED`를 취소 후 정상 종료 상태로 처리하도록 변경했다.

```javascript
if (status.status === "UPLOADED") {
  // 상태 조회 종료 및 목록 갱신
}
```

### 6. 검증 방법

다음 시나리오로 검증했다.

1. 테스트 계정 생성
2. PDF 계약서 업로드
3. 분석 시작 API 호출
4. 분석 도중 취소 API 호출
5. 취소 응답 상태 확인
6. 계약서 상태 재조회
7. 취소된 결과가 저장되지 않는지 확인
8. 같은 계약서를 다시 분석할 수 있는지 확인

최종 결과:

```text
취소 API: 정상 응답
계약서 상태: UPLOADED
분석 결과: 저장되지 않음
재분석: 가능
```

### 7. 배운 점

#### Enum 변경은 코드 변경만으로 끝나지 않는다

JPA enum에 값을 추가할 때는 운영 또는 기존 개발 DB의 컬럼 제약조건까지 확인해야 한다.
프로덕션 환경에서는 Flyway나 Liquibase 같은 명시적 마이그레이션 도구를 사용하는 것이 안전하다.

#### 새 DB 테스트만으로는 마이그레이션 문제를 발견할 수 없다

새 DB는 최신 엔티티 기준으로 스키마를 만들기 때문에 정상 동작할 수 있다. 기존 버전에서 만들어진
DB를 유지한 상태로 업그레이드 테스트를 별도로 수행해야 한다.

#### 비동기 취소는 UI와 서버 상태를 함께 설계해야 한다

버튼만 비활성화하는 것은 취소가 아니다. 작업 중단, 결과 저장 차단, DB 상태 복구, 프론트 폴링 종료가
하나의 흐름으로 처리돼야 한다.

#### 실패한 요청이 상태 관찰까지 중단하면 안 된다

취소 요청이 실패하더라도 상태 조회는 계속되어야 한다. 그렇지 않으면 서버 작업은 끝났는데 화면만
영원히 `처리 중...`으로 남을 수 있다.

### 8. 향후 개선

- Flyway를 도입해 상태 enum 및 체크 제약조건 변경을 버전 관리한다.
- 애플리케이션 재시작 시 오래된 `PROCESSING` 작업을 복구하는 로직을 추가한다.
- 취소 요청과 분석 완료가 동시에 발생하는 경쟁 조건을 통합 테스트한다.
- 작업 ID와 취소 시각을 별도 테이블에 저장해 분석 작업 이력을 관리한다.
- FastAPI와 Ollama까지 취소 신호가 전달됐는지 관찰할 수 있는 로그와 메트릭을 추가한다.

## PDF 분석 리포트의 글자가 표 밖으로 넘어가고 항목 구분이 어려운 문제

### 1. 배경

LAWZIC은 계약서 분석 결과를 ReportLab으로 PDF 리포트로 생성한다. 리포트에는 다음 정보가 포함된다.

- 종합 위험도와 위험 점수
- 계약서 요약
- 표준근로계약서 체크리스트
- 위험조항 원문
- 판단 이유와 권고
- 안전한 대체 문구
- 관련 법령 출처

초기 구현에서는 체크리스트 데이터를 일반 문자열로 `Table`에 전달하고, 위험조항의 각 내용을
연속된 문단으로 출력했다.

### 2. 발생한 증상

#### 체크리스트 표 오버플로

`확인 근거`가 길어지면 문자열이 셀 너비에 맞춰 줄바꿈되지 않고 오른쪽 표 경계를 넘어갔다.

```text
| 항목 | 상태 | 확인 근거                                      |
| 임금 | ...  | 계약서에서 추출한 긴 문장이 표 바깥까지 출력됨 → |
```

#### 위험조항의 낮은 가독성

위험조항이 다음과 같이 라벨과 내용 사이의 구분 없이 이어져 보였다.

```text
원문 퇴직금은 월급에 포함되어 있습니다.
판단 이유 퇴직급여 지급 조건이 명시되지 않아 검토가 필요합니다.
권고 퇴직금 지급 방법을 명확하게 작성하세요.
```

내용이 길어질수록 `원문`, `판단 이유`, `권고`, `대체 문구`의 경계를 빠르게 파악하기 어려웠다.

### 3. 근본 원인

#### ReportLab `Table`의 일반 문자열은 자동 줄바꿈되지 않는다

초기 체크리스트는 다음과 같이 일반 문자열 배열로 구성했다.

```python
checklist.append([
    item.title,
    item.status,
    item.evidence,
])
```

ReportLab의 `Table`은 문자열을 셀 너비에 맞춰 자동으로 문단 배치하지 않는다. 따라서 문자열의
렌더링 폭이 지정된 `colWidths`보다 길면 셀 밖으로 그대로 출력될 수 있다.

열 너비를 지정하는 것만으로는 해결되지 않았다.

```python
Table(checklist, colWidths=[90, 65, 315])
```

`colWidths`는 셀 영역의 크기만 결정하며, 셀 안의 일반 문자열에 줄바꿈 규칙을 적용하지 않는다.

#### 위험조항을 연속된 `Paragraph`로만 출력했다

초기 위험조항은 다음 구조였다.

```python
Paragraph(f"<b>원문</b> {clause.original_text}", body)
Paragraph(f"<b>판단 이유</b> {clause.reason}", body)
Paragraph(f"<b>권고</b> {clause.recommendation}", body)
```

굵은 라벨만 추가했기 때문에 내용이 길면 각 항목이 하나의 긴 문단처럼 보였다. 라벨 너비와 내용
시작 위치도 일정하지 않아 시각적인 정렬이 부족했다.

### 4. 해결 방법

#### 셀 데이터를 `Paragraph`로 변환

체크리스트의 모든 셀을 `Paragraph`로 감싸고 CJK 줄바꿈 스타일을 적용했다.

```python
cell = ParagraphStyle(
    "LawzicCell",
    parent=body,
    fontSize=8,
    leading=12,
    wordWrap="CJK",
)

checklist.append([
    Paragraph(item.title, cell),
    Paragraph(status_label, cell),
    Paragraph(item.evidence or "계약서에서 확인되지 않음", cell),
])
```

이제 긴 한글 문장이 셀 너비에 맞춰 여러 줄로 배치되고, 행 높이도 내용에 맞게 자동으로 증가한다.

#### 표 여백과 정렬 조정

텍스트가 테두리에 붙지 않도록 셀별 패딩과 상단 정렬을 적용했다.

```python
TableStyle([
    ("VALIGN", (0, 0), (-1, -1), "TOP"),
    ("LEFTPADDING", (0, 0), (-1, -1), 7),
    ("RIGHTPADDING", (0, 0), (-1, -1), 7),
    ("TOPPADDING", (0, 0), (-1, -1), 7),
    ("BOTTOMPADDING", (0, 0), (-1, -1), 7),
])
```

#### 위험조항을 라벨 열과 내용 열로 분리

각 위험조항을 2열 표로 변경했다.

```text
┌──────────┬────────────────────────────────────┐
│ 원문:     │ 퇴직금은 월급에 포함되어 있습니다. │
├──────────┼────────────────────────────────────┤
│ 판단 이유:│ 퇴직급여 지급 조건이 불명확합니다.  │
├──────────┼────────────────────────────────────┤
│ 권고:     │ 지급 요건과 방법을 명시하세요.       │
├──────────┼────────────────────────────────────┤
│ 대체 문구:│ 퇴직급여는 관계 법령에 따라...       │
└──────────┴────────────────────────────────────┘
```

구현에서는 라벨 열의 너비를 고정하고 배경색을 적용해 항목의 경계를 명확하게 했다.

```python
Table(field_rows, colWidths=[72, 398])
```

내용 열에는 `Paragraph`와 `wordWrap="CJK"`를 적용해 긴 원문과 설명도 표 내부에서 줄바꿈되도록 했다.

#### 페이지 하단의 조항 잘림 방지

페이지에 남은 공간이 너무 적을 때 새 위험조항 제목만 하단에 남는 문제를 방지하기 위해
`CondPageBreak`를 추가했다.

```python
story.append(CondPageBreak(120))
```

최소 공간이 부족하면 다음 페이지에서 해당 조항을 시작한다.

#### 특수문자 이스케이프

계약서 원문에 `&`, `<`, `>` 등이 포함되면 `Paragraph`가 이를 마크업으로 해석할 수 있다.
사용자 입력값을 `html.escape()`로 처리해 PDF 생성 오류와 예상하지 못한 서식 변형을 방지했다.

```python
Paragraph(escape(clause.original_text), field_value)
```

### 5. 검증 방법

단순 텍스트 추출만으로는 PDF 레이아웃 문제를 확인할 수 없으므로 다음 절차로 검증했다.

1. 실제보다 긴 체크리스트 근거 문장을 테스트 데이터에 삽입
2. 수정된 ReportLab 코드로 PDF 생성
3. Poppler `pdftoppm`으로 모든 페이지를 PNG 이미지로 렌더링
4. 표 경계, 자동 줄바꿈, 행 높이, 항목 간격을 시각적으로 확인
5. 위험조항의 원문·판단 이유·권고·대체 문구 구분 확인
6. 임시 렌더링 이미지를 삭제하고 검증용 PDF만 보관

최종 검증 결과:

```text
긴 확인 근거: 셀 내부 자동 줄바꿈
표 경계 침범: 없음
글자 겹침 및 잘림: 없음
한글 글꼴 깨짐: 없음
위험조항 항목 구분: 정상
페이지 전환: 정상
```

### 6. 배운 점

#### PDF 표의 열 너비와 텍스트 줄바꿈은 별개의 문제다

`colWidths`를 설정했다고 해서 셀 안의 문자열이 자동으로 줄바꿈되는 것은 아니다. ReportLab 표에서
가변 길이 텍스트를 다룰 때는 `Paragraph` 같은 Flowable을 사용해야 한다.

#### 데이터가 정확해도 정보 구조가 나쁘면 사용하기 어렵다

원문, 판단 이유, 권고가 모두 포함돼 있어도 시각적 계층이 없으면 사용자가 내용을 빠르게 비교할 수
없다. 보고서에서는 정보의 존재뿐 아니라 라벨, 정렬, 여백과 그룹화가 중요하다.

#### PDF는 반드시 렌더링 결과를 확인해야 한다

PDF 파일 생성 성공이나 텍스트 추출 성공은 레이아웃 정상 여부를 보장하지 않는다. 실제 페이지를
이미지로 렌더링해 잘림, 겹침, 표 경계 침범과 글꼴 문제를 확인해야 한다.

### 7. 향후 개선

- 위험조항이 여러 페이지에 걸릴 때 표 헤더를 반복 표시한다.
- 위험도에 따라 제목과 라벨 색상을 다르게 적용한다.
- 체크리스트의 누락 항목을 아이콘이나 강조색으로 구분한다.
- 페이지 번호, 생성 시각과 문서 식별자를 바닥글에 추가한다.
- 다양한 길이의 계약서 데이터를 사용하는 PDF 레이아웃 회귀 테스트를 구축한다.

## 체크리스트가 `지급일이 휴일` 문장을 휴일 조항의 근거로 잘못 연결한 문제

### 1. 증상

근로계약서에는 다음 두 문장이 함께 있었다.

```text
제4조 (임금)
지급일이 휴일인 경우에는 그 전 영업일에 지급한다.

제6조 (휴일)
주휴일은 매주 일요일로 한다.
```

그러나 분석 리포트의 `휴일` 체크리스트에는 실제 제6조가 아니라 임금 조항의
`지급일이 휴일인 경우`가 확인 근거로 표시됐다.

### 2. 근본 원인

필수항목의 근거를 선택할 때 문서에서 키워드가 처음 나타난 위치만 사용했다.

```python
keyword = next(item for item in keywords if item in text)
position = text.index(keyword)
evidence = context(text, position)
```

`휴일`이라는 단어가 제6조보다 제4조의 지급일 문장에서 먼저 등장했기 때문에, 의미와 무관하게
첫 번째 문장이 근거로 채택됐다. 이는 OCR 자체의 오류가 아니라 추출된 텍스트에서 근거를 고르는
문맥 선택 알고리즘의 문제였다.

### 3. 해결

단순 최초 일치 방식을 제거하고 조항 단위 문맥 점수 방식을 적용했다.

1. `제N조` 제목부터 다음 조항 전까지를 하나의 후보 문맥으로 분리한다.
2. 체크리스트 키워드가 포함된 모든 조항을 후보로 수집한다.
3. 조항 제목과 의미상 관련된 표현에는 가점을 부여한다.
4. 우연히 같은 단어가 사용된 문맥에는 감점을 부여한다.
5. 최소 점수보다 낮으면 필수 조항의 근거로 인정하지 않는다.

휴일 항목의 주요 신호는 다음과 같다.

```text
긍정 신호:
- 제N조 (휴일)
- 주휴일
- 매주 일요일
- 유급휴일
- 근로자의 날

부정 신호:
- 지급일이 휴일
- 지급일이 공휴일
- 휴일인 경우 그 전 영업일
```

따라서 실제 휴일 조항이 있으면 제6조를 선택하고, `지급일이 휴일`이라는 문장만 있다면 휴일
필수항목을 `MISSING`으로 판단한다.

### 4. 회귀 테스트

다음 두 시나리오를 자동 테스트로 추가했다.

```text
시나리오 A
임금 조항의 지급일 휴일 문구 + 실제 휴일 조항 존재
→ 휴일 상태 PRESENT
→ 근거는 제6조 (휴일)

시나리오 B
임금 조항의 지급일 휴일 문구만 존재
→ 휴일 상태 MISSING
→ 근거 없음
```

전체 AI 테스트 결과는 `8 passed`이다.

### 5. 배운 점

- 키워드가 포함됐다는 사실과 해당 키워드가 검토 대상 의미로 사용됐다는 사실은 다르다.
- RAG와 문서 분석에서는 첫 번째 검색 결과보다 조항 제목과 주변 의미를 함께 평가해야 한다.
- OCR 오류와 문맥 선택 오류를 구분해야 올바른 계층을 수정할 수 있다.
- 근거 표시 기능은 분석 결과만큼 중요하며, 잘못된 근거는 전체 분석의 신뢰도를 떨어뜨린다.

## 계약서에 이미 기재된 내용을 LLM이 다시 권고한 문제

### 1. 증상

계약서에 임금 구성항목, 산정기간, 지급일과 지급방법이 모두 기재되어 있었지만 LLM은 다음과 같은
일반적인 권고를 생성했다.

```text
임금 지급 내용에 관한 구체적인 내용을 명확히 작성하세요.
```

체크리스트는 임금 항목을 `PRESENT`로 판단했지만 위험조항 목록에는 임금 관련 보완 권고가 동시에
표시되어 결과가 서로 모순됐다.

### 2. 원인

- LLM 프롬프트가 위험이나 누락을 적극적으로 찾도록 작성되어 있었다.
- LLM이 조항을 선택하면 구조화 출력상 반드시 `recommendation`을 생성해야 했다.
- 체크리스트 결과와 LLM 위험조항을 비교하는 검증 단계가 없었다.
- 검색된 법령의 일반적인 의무를 계약서의 실제 미충족 사항으로 잘못 해석할 수 있었다.
- 작은 로컬 모델이 `법적 요구사항`과 `이미 충족된 요구사항`을 안정적으로 구별하기 어려웠다.

### 3. 해결

프롬프트에 이미 충족된 사항을 위험조항으로 만들지 말라는 지시를 추가하고, 별도의 결정론적
후처리 검증기를 구현했다.

```text
LLM 위험조항 생성
→ 의미 기반 조항 유형 분류
→ 관련 체크리스트 PRESENT 여부 확인
→ 계약서 전체에서 세부 충족요건 검증
→ 이미 충족된 일반 권고 제거
→ 남은 항목 비율만큼 LLM 점수 보정
→ 규칙 기반 위험조항과 최종 병합
```

검증 항목은 임금, 근로시간, 휴일, 연차, 퇴직급여와 계약 종료를 포함한다. 예를 들어 임금은
구성항목, 산정기간, 지급 여부와 지급방법이 모두 존재할 때 일반적인 명시 권고를 제거한다.

### 4. 실제 위험을 숨기지 않기 위한 보호장치

체크리스트가 `PRESENT`라고 해서 모든 LLM 결과를 제거하지 않는다. 원문에 다음과 같은 명시적
위험 표현이 있으면 후처리 제거 대상에서 제외한다.

```text
무급
임금 또는 급여에서 공제
퇴직금이 임금에 포함
위약금
손해 전액 배상
임금 감액
즉시 또는 일방적 해고
권리 포기
```

따라서 `임금 항목이 존재한다`는 사실 때문에 `임금에서 손해액을 공제한다`는 실제 위험조항이
사라지는 문제를 방지했다.

### 5. 점수 보정

중복 권고를 제거하고도 기존 LLM 점수를 그대로 유지하면 목록과 점수가 불일치한다. 제거 전후 LLM
조항 수의 비율로 점수를 조정하고, 규칙 기반 점수보다 낮아지지 않도록 최종 점수를 계산했다.

```text
검증된 LLM 점수 = 기존 LLM 점수 × 유지된 조항 수 / 원래 조항 수
최종 점수 = max(검증된 LLM 점수, 규칙 기반 점수)
```

### 6. 회귀 테스트

- 임금 세부조건이 모두 기재된 계약서의 일반적인 임금 권고가 제거되는지 확인
- 중복 권고가 전부 제거되면 점수가 `0 / SAFE`로 보정되는지 확인
- `임금에서 공제`라는 명시적 위험조항은 제거되지 않는지 확인

전체 AI 테스트 결과는 `10 passed`이다.

## 메인 제목의 어색한 줄바꿈과 분석 이력 카드 확장 문제

### 1. 증상

화면 너비가 약 800px일 때 메인 제목의 마지막 단어가 다음처럼 글자 중간에서 분리됐다.

```text
계약서의 위험을
근거와 함께 확인하
세요.
```

계약서 분석실에서는 긴 파일명과 작업 버튼이 한 줄에 함께 배치되면서 파일명이 글자 단위로
지나치게 잘게 나뉘고, 버튼이 카드 밖으로 밀려났다. 분석 이력이 추가될수록 분석 이력 카드의
높이도 계속 증가해 오른쪽 분석 결과 영역과 전체 페이지 레이아웃을 불필요하게 늘렸다.

### 2. 원인

- 메인 제목에 강제 `<br>`가 들어가 있어 반응형 너비에 맞춰 브라우저가 줄을 조정할 수 없었다.
- 한글 제목에 `word-break: keep-all`이 없어 단어 중간에서도 줄바꿈이 허용됐다.
- 모바일 구간에서도 제목 크기가 크게 유지되어 사용할 수 있는 가로 공간이 부족했다.
- 분석 이력 한 건을 `display: flex`로 구성해 긴 파일명과 버튼 행이 가로 공간을 경쟁했다.
- 분석 이력 카드와 목록 영역에 최대 높이 및 `overflow-y` 설정이 없었다.
- 파일명 영역에 `min-width: 0`과 긴 문자열 처리 규칙이 없어 flex/grid 자식이 정상적으로
  축소되지 않았다.

### 3. 해결

메인 제목을 문법적으로 자연스러운 두 개의 의미 단위로 분리했다.

```jsx
<h1>
  <span className="hero-title-line">계약서의 위험을</span>
  <span className="hero-title-line accent">근거와 함께 확인하세요.</span>
</h1>
```

제목과 소개 문장에는 한글 단어를 보존하는 줄바꿈 규칙을 적용하고, 작은 화면에서는
`clamp()`를 사용해 글자 크기가 화면 너비에 맞춰 줄어들도록 했다.

```css
.hero-copy h1 {
  word-break: keep-all;
  overflow-wrap: normal;
  text-wrap: balance;
}

.hero-title-line {
  display: block;
}

.hero-copy > p:not(.hero-kicker) {
  word-break: keep-all;
}
```

분석 이력은 카드 제목과 스크롤 가능한 목록을 분리했다.

```jsx
<section className="card list">
  <h3>분석 이력</h3>
  <div className="contract-list">
    {/* 계약서 이력 */}
  </div>
</section>
```

카드 자체는 최대 높이를 유지하고 목록만 스크롤되도록 설정했다. 계약서 한 건은 파일 정보와
버튼 행을 위아래로 배치하고, 버튼은 동일한 너비의 3열 grid로 정렬했다.

```css
.list {
  max-height: 440px;
  display: flex;
  flex-direction: column;
  overflow: hidden;
}

.contract-list {
  min-height: 0;
  overflow-y: auto;
  overscroll-behavior: contain;
  scrollbar-gutter: stable;
}

.contract {
  display: grid;
}

.contract-info {
  min-width: 0;
}

.contract strong {
  overflow-wrap: anywhere;
}

.contract-actions {
  display: grid;
  grid-template-columns: repeat(3, minmax(0, 1fr));
}
```

모바일 화면에서는 분석 이력 카드의 최대 높이를 `420px`로 조정했다.

### 4. 검증

- 800px 너비에서 제목이 두 개의 의미 단위로 표시되는지 확인
- 제목과 소개 문장이 한글 단어 중간에서 분리되지 않는지 확인
- 페이지의 가로 스크롤이 발생하지 않는지 확인
- 긴 계약서 파일명이 카드 내부에서 줄바꿈되는지 확인
- 버튼 3개가 카드 경계를 넘어가지 않는지 확인
- 분석 이력이 증가해도 카드 높이가 고정되고 목록 내부에 세로 스크롤이 생기는지 확인
- Vite 프로덕션 빌드 성공 확인

### 5. 배운 점

- 한글 UI는 영문과 달리 기본 줄바꿈이 음절 단위로 발생할 수 있으므로 제목과 짧은 설명에는
  `word-break: keep-all`을 명시하는 것이 안전하다.
- 중요한 제목은 화면 위치를 기준으로 강제 개행하기보다 의미 단위로 구조화해야 반응형 화면에서도
  문장이 자연스럽다.
- 반복 데이터가 들어가는 패널은 콘텐츠 수에 따라 전체 레이아웃이 커지지 않도록 높이 제한과
  내부 스크롤 정책을 처음부터 정해야 한다.
- 긴 파일명과 작업 버튼을 같은 가로 flex 행에 두면 좁은 카드에서 쉽게 충돌하므로 정보 영역과
  작업 영역을 분리하는 것이 안정적이다.

## 안전한 부정문을 위험조항으로 오탐한 문제와 의미 기반 회귀 테스트

### 1. 증상

정상 조항인 `회사는 확정되지 않은 손해액을 임금에서 임의로 공제하지 않는다.`가 다음 두 위험으로 잘못 탐지되었다.

- 임금의 임의 공제
- 손해액의 임금 공제

실제로는 임금 공제를 금지하는 문장인데 시스템이 공제를 허용하는 문장으로 반대로 해석한 것이다.

### 2. 원인

기존 위험 규칙은 문장의 의미 구조보다 `손해액`, `임금`, `공제` 같은 단어의 동시 출현 여부를 중심으로 판단했다. 정규식이 `공제`까지 일치한 뒤에 나오는 `하지 않는다`를 반영하지 못했으며, 유사한 두 규칙이 같은 문장에 동시에 일치해 결과도 중복되었다.

즉, 다음 정보를 구분하는 과정이 부족했다.

- 행위의 주체
- 위험 행위와 대상
- 허용·금지 여부
- 조건 또는 부정 표현이 어느 행위를 수식하는지

### 3. 해결

`ai/app/semantic.py`에 의미 기반 검증 단계를 추가했다.

- 계약서 원문을 `제N조` 단위로 분리한다.
- 위험 후보에서 주체·행위·대상·조건·부정 여부를 추출한다.
- 위험 유형별 안전한 부정 표현을 검사한다.
- 첫 번째 후보가 안전한 부정문이면 건너뛰고 이후의 실제 위험 문장을 계속 탐색한다.
- 규칙 결과와 LLM 결과를 원문 근거를 기준으로 상호 검증한다.
- 근거가 부족한 LLM 단독 결과는 위험으로 단정하지 않고 `검토 필요`로 처리한다.
- 정상 조항이나 위험 의미가 없는 일반 설명은 분석 결과에서 제거한다.

분석 결과에는 판단 과정을 확인할 수 있도록 `confidence`, `review_required`, `semantic` 정보도 포함했다.

### 4. 의미 기반 회귀 데이터셋 추가

같은 문제가 다른 계약서에서 다시 발생하지 않도록 `ai/tests/data/semantic_contract_cases.json`에 정상·위험 문장 데이터셋을 만들고 `ai/tests/test_semantic_dataset.py`에서 전체 사례를 자동 검증하도록 했다.

현재 회귀 사례에는 다음 내용이 포함된다.

- 임금 공제를 금지한 정상 조항
- 확정되지 않은 손해액 공제를 금지한 정상 조항
- 실제 임의 공제 및 손해액 공제
- 휴게시간 미보장
- 무급 연장근로
- 연차 포기
- 퇴직금 미지급
- 퇴사 제한과 위약금
- 민원·소송 포기 강요

최종 위험 판정뿐 아니라 조항 분리와 주체·행위·대상·부정 여부 추출 결과도 함께 검사한다.

### 5. 검증 결과

- 정상 계약서 `표준근로.pdf`: `SAFE`, 위험 점수 `0`, 위험조항 없음
- 심각한 하자 계약서: `HIGH`, 위험 점수 `100`, 위험조항 14개 탐지
- 전체 AI 테스트: `29 passed`

특정 문장을 예외 처리한 것이 아니라 정상 문장과 실제 위험 문장을 함께 구분하는 회귀 검증 체계를 마련했다.

### 6. 배운 점

- 법률 문장은 단어 포함 여부만으로 판정하면 부정문을 반대로 해석하기 쉽다.
- 위험 탐지는 `주체 + 행위 + 대상 + 부정/조건`의 의미 구조를 기준으로 해야 한다.
- LLM 출력도 그대로 노출하지 않고 규칙 및 원문 근거와 교차 검증해야 한다.
- 오류 수정 시 해당 사례를 데이터셋에 추가하고 전체 회귀 테스트를 실행해야 재발을 막을 수 있다.

## 체크리스트 클릭 시 PDF 페이지 전체가 하이라이트된 문제

### 1. 증상

분석 결과의 체크리스트에서 `임금` 같은 항목을 클릭하면 해당 조항만 표시되지 않고 PDF 페이지의 대부분이 노란색으로 하이라이트되었다.

### 2. 원인

기존 `locate_text()`는 근거 문장을 토큰으로 나눈 뒤 페이지에서 토큰 하나라도 포함한 모든 단어를 수집했다.

`근로`, `시간`, `한다`처럼 계약서 전체에서 반복되는 단어까지 모두 일치했고, 수집된 좌표 전체의 최솟값과 최댓값으로 하나의 사각형을 만들었다. 이 때문에 서로 멀리 떨어진 여러 조항이 하나의 큰 영역으로 합쳐졌다.

### 3. 해결

`ai/app/document_features.py`의 PDF 위치 탐색 방식을 다음과 같이 변경했다.

- 검색 문장과 PDF 단어 배열에서 가장 긴 연속 일치 구간을 찾는다.
- 두 단어 이상 연속으로 일치하는 구간을 우선 사용한다.
- 충분한 연속 일치가 없으면 유사도가 가장 높은 한 줄만 사용한다.
- PyMuPDF의 블록 번호와 줄 번호를 기준으로 일치 단어를 묶는다.
- 서로 다른 줄을 하나의 큰 사각형으로 합치지 않고 줄마다 작은 좌표 상자를 만든다.

반복 키워드가 다른 조항에 있어도 선택한 체크리스트의 실제 근거 문장 주변만 강조되도록 수정했다.

### 4. 회귀 테스트 추가

`ai/tests/test_document_features.py`에 페이지 위·중간·아래에 같은 일반 단어가 반복되는 가상 PDF 사례를 추가했다.

테스트는 다음을 검증한다.

- 검색 대상인 `제2조` 부근의 좌표만 반환되는지
- 페이지 아래쪽의 같은 단어가 함께 선택되지 않는지
- 하이라이트 상자의 높이가 한 줄 수준으로 제한되는지

### 5. 검증 결과

`표준근로.pdf`로 위치를 다시 계산한 결과 임금, 근로시간, 휴일, 연차 항목이 각각 해당 조항의 몇 개 줄에만 매핑되었으며 페이지 전체 크기의 하이라이트는 생성되지 않았다.

수정 후 전체 AI 테스트는 `29 passed`로 완료되었다.

### 6. 배운 점

- 문서 하이라이트는 키워드 존재 여부보다 문장 내 연속성과 줄 구조가 중요하다.
- 여러 좌표를 단순히 하나의 최소·최대 사각형으로 합치면 멀리 떨어진 문장까지 모두 강조될 수 있다.
- PDF 위치 추출도 반복 단어가 많은 실제 문서 구조를 반영한 회귀 테스트가 필요하다.

## 분석 결과가 HIGH에 편중되고 LOW·MEDIUM이 잘 나오지 않은 문제

### 1. 증상

계약서를 분석하면 위험조항 탐지 자체는 정상적으로 동작했지만, 결과가 대부분 `HIGH`로 표시되고 `LOW`나 `MEDIUM` 등급은 거의 나타나지 않았다.

또한 확정된 위험이 아닌 `검토 필요` 항목과 LLM이 자체적으로 생성한 종합 점수도 최종 위험도에 영향을 주고 있었다.

### 2. 원인

기존 점수 계산에는 다음 문제가 있었다.

- `검토 필요` 항목도 한 건당 2점씩 종합 위험 점수에 포함되었다.
- 같은 원문이 유사한 여러 위험 규칙에 일치하면 각각 점수가 더해질 수 있었다.
- 규칙 기반 점수와 LLM이 반환한 `overall_score` 중 높은 값을 최종 점수로 사용했다.
- LLM이 높은 점수를 반환하면 검증된 위험조항 수가 적어도 최종 결과가 `HIGH`가 될 수 있었다.
- SAFE·LOW·MEDIUM·HIGH 등급별 대표 계약서를 이용한 분포 회귀 테스트가 없었다.

결과적으로 애매한 항목, 중복 위험, 검증되지 않은 LLM 점수가 누적되면서 종합 위험도가 실제보다 높아질 가능성이 있었다.

### 3. 점수 계산 정책 변경

최종 위험 점수는 검증된 조항만 사용하도록 `calculate_verified_risk()`로 계산 방식을 통합했다.

현재 가중치는 다음과 같다.

- 확정 `HIGH`: 8점
- 확정 `MEDIUM`: 4점
- 확정 `LOW`: 2점
- `검토 필요`: 0점

최종 등급 기준은 다음과 같다.

- 0점: `SAFE`
- 1~24점: `LOW`
- 25~59점: `MEDIUM`
- 60점 이상: `HIGH`

검토 필요 항목만 존재하고 확정된 위험이 없다면 종합 점수는 0점, 종합 위험도는 `SAFE`로 표시한다. 검토가 필요하다는 사실은 별도 건수로 제공한다.

### 4. 검토 필요 항목 분리

분석 응답 모델에 `review_required_count`를 추가했다.

프론트 화면과 PDF 분석 리포트에는 다음처럼 종합 위험도와 별도로 표시한다.

> 종합 위험도 SAFE · 0점
>
> 별도 검토 필요 2건

이 방식으로 확정된 위험과 자동 분석만으로 판단하기 어려운 항목을 명확히 구분했다.

### 5. 같은 원문의 유사 위험 중복 제거

`deduplicate_findings()`를 추가해 동일한 원문에서 파생된 유사 위험은 가장 확실한 한 건만 유지하도록 했다.

예를 들어 같은 문장이 다음 두 유형에 동시에 일치하더라도 임금 공제 위험군 한 건으로 계산한다.

- `ARBITRARY_WAGE_DEDUCTION`
- `DAMAGE_WAGE_DEDUCTION`

중복 후보 중에서는 다음 우선순위로 대표 항목을 선택한다.

1. `검토 필요`가 아닌 확정 항목
2. 위험 가중치가 높은 항목
3. 분석 확신도가 높은 항목

서로 다른 필수 조항의 누락처럼 독립적으로 유지해야 하는 결과는 중복 제거 대상에서 제외했다.

### 6. LLM 종합 점수 제거

LLM 응답의 `overall_score`를 최종 점수 계산에 사용하지 않도록 변경했다.

LLM은 위험 후보와 설명을 제안할 수 있지만 다음 검증을 통과한 조항만 종합 점수에 반영한다.

- 계약서 원문에서 근거가 확인되는지
- 규칙 결과와 일치하는지
- 안전한 부정문이 아닌지
- 검토 필요가 아닌 확정 위험인지
- 동일 원문의 유사 위험과 중복되지 않는지

최종 점수는 병합과 후처리가 끝난 조항 목록을 기준으로 서버에서 다시 계산한다.

### 7. 등급별 회귀 데이터셋 추가

`ai/tests/data/risk_grade_contract_cases.json`에 다음 네 종류의 대표 근로계약서를 추가했다.

- 위험이 없는 완전한 계약서: `SAFE`
- 확정 위험이 한 건인 계약서: `LOW`
- 확정 위험이 여러 건인 계약서: `MEDIUM`
- 다수의 중대한 위험이 포함된 계약서: `HIGH`

`ai/tests/test_risk_grades.py`에서는 다음 내용을 자동 검증한다.

- 대표 계약서별 예상 위험 등급
- 검토 필요 항목이 점수를 올리지 않는지
- 검토 필요 건수가 별도로 계산되는지
- 같은 원문의 유사 위험이 한 번만 가점되는지

### 8. 검증 결과

- AI 전체 테스트: `35 passed`
- 프론트 프로덕션 빌드: 성공
- Python 애플리케이션 및 테스트 파일 컴파일: 성공

기존에 저장된 분석 결과에는 이전 점수 체계가 남아 있을 수 있으므로 새 정책을 적용하려면 계약서를 재분석해야 한다.

### 9. 배운 점

- 불확실성은 위험 점수에 섞기보다 별도 지표로 제공해야 결과를 오해하지 않는다.
- LLM이 생성한 종합 점수는 설명용 참고값으로도 일관성이 부족하므로 검증된 세부 결과에서 다시 계산해야 한다.
- 규칙 개수가 늘어나면 동일 의미 위험의 중복 가점을 반드시 통제해야 한다.
- 탐지 정확도뿐 아니라 SAFE·LOW·MEDIUM·HIGH 등급 분포도 회귀 테스트로 관리해야 한다.

## `근무시간`과 `월요일~금요일`을 근로시간·휴일 완전 누락으로 오판한 문제

### 1. 증상

실제 계약서에는 다음과 같은 조항이 있었다.

```text
제4조 근무시간
월요일~금요일 09:00~18:00 (휴게 12:00~13:00)
```

사람이 읽으면 근무 요일, 시작·종료 시각, 휴게시간이 명시되어 있다는 것을 확인할 수 있다.
하지만 자동 분석 결과에는 다음 두 위험이 동시에 표시되었다.

```text
근로시간 조항 누락 가능성
휴일 조항 누락 가능성
```

근로시간은 명백한 오탐이었다. 휴일도 명시적인 유급 주휴일 조항은 아니지만 월요일부터
금요일까지 근무한다고 적혀 있어 관련 근거가 전혀 없는 완전 누락으로 단정하기에는
부정확했다.

### 2. 재현 및 원문 검증

PDF를 Poppler로 PNG 렌더링해 시각적으로 확인하고, 실제 서비스가 사용하는 PyMuPDF
추출기 `extract_document()`로 다시 읽었다.

추출 결과에도 다음 문장이 정상적으로 존재했다.

```text
제4조 근무시간
월요일~금요일 09:00~18:00 (휴게 12:00~13:00)
```

따라서 PDF 폰트나 텍스트 추출 실패가 아니라 추출된 문장을 평가하는 체크리스트 규칙과
최종 병합 로직의 문제임을 확인했다.

### 3. 근본 원인

#### 조항 제목 동의어에 서로 다른 가중치를 적용

기존 분석기는 `근무시간`을 일반 키워드로는 알고 있었지만, 조항 제목이 정확히
`근로시간`일 때만 제목 일치 가중치를 부여했다.

```text
제4조 근로시간 → 강한 근거
제4조 근무시간 → 약한 키워드 한 건
```

`근무시간`은 실제 계약서에서 흔히 사용하는 동의어인데도 근거 점수 기준을 넘지 못해
누락으로 처리되었다.

#### 실제 시간 범위 표기를 강한 근거로 인식하지 못함

기존 신호는 주로 `시부터`, `시까지`, `1일`, `1주`, `소정근로시간` 같은 문구를
찾았다. `09:00~18:00`처럼 숫자와 기호로 작성된 시간 범위는 별도의 의미 패턴으로
평가하지 않았다.

#### 휴일 판정에 간접 근거 상태가 없음

기존 휴일 체크리스트는 다음과 같은 명시적 표현만 정상 근거로 인정했다.

- 주휴일
- 매주 일요일
- 유급휴일
- 휴일을 보장한다

`월요일~금요일`이나 `주 5일` 같은 문장은 휴일과 관련된 간접 근거이지만, 기존
상태 모델에는 `간접 근거가 있으나 법적 유급 주휴일까지 확정할 수 없음`을 표현할
방법이 없었다. 그 결과 명시적 휴일 단어가 없으면 곧바로 `MISSING`이 되었다.

#### 체크리스트·위험규칙·LLM 결과를 병합한 뒤 충돌을 검사하지 않음

분석 단계가 각각 결과를 만든 뒤 단순 병합되는 구조에서는 다음과 같은 모순이 최종
리포트에 함께 남을 수 있었다.

```text
체크리스트: 근로시간 근거 문장 존재
위험조항: MISSING_WORK_HOURS
```

규칙 결과를 수정하더라도 LLM이 `휴일`이라는 직접 표현이 없다는 이유로
`MISSING_HOLIDAY`를 다시 제안할 가능성도 있었다.

### 4. 해결 방법

#### 동의어를 조항 제목으로 동일하게 인정

근로시간 조항의 제목 별칭을 다음처럼 정의했다.

```text
근로시간
근무시간
소정근로시간
```

이제 `제4조 근무시간`도 정식 근로시간 조항 제목으로 높은 근거 점수를 받는다.

#### 시간 범위 의미 패턴 추가

`TIME_RANGE_PATTERN`을 추가해 다음 표기를 근로시간의 강한 근거로 처리했다.

```text
09:00~18:00
09:00-18:00
09시~18시
09시부터 18시까지
```

단순 단어 포함 여부가 아니라 시작 시각과 종료 시각이 함께 있는 시간 범위 구조를
확인한다.

#### 휴일 판정을 3단계로 구분

휴일 관련 결과를 다음 정책으로 변경했다.

| 원문 근거 | 체크리스트 상태 | 처리 |
|---|---|---|
| `주휴일은 매주 일요일로 한다` 등 명시적 근거 | `COMPLIANT` | 정상 근거 |
| `월요일~금요일`, `주 5일` 등 간접 근거 | `REVIEW` | 완전 누락에서 제외하고 별도 검토 |
| 근무일·휴일 관련 근거가 전혀 없음 | `MISSING` | 누락 가능성 표시 |

간접 근거만으로 유급 주휴일을 확정하지 않으면서도 관련 내용이 전혀 없다고 잘못
단정하지 않도록 했다.

#### 최종 충돌 검증 단계 추가

`reconcile_checklist_findings()`를 추가해 체크리스트와 누락 위험을 최종 리포트 생성
직전에 대조한다.

```text
MISSING_WORK_HOURS 후보 생성
→ WORK_HOURS 체크리스트 근거 확인
→ COMPLIANT 또는 REVIEW이면 누락 후보 제거
```

동일한 검증을 임금, 근로시간, 휴일, 연차 누락 유형에 공통으로 적용한다.

#### LLM 누락 결과도 체크리스트로 재검증

LLM이 `누락` 위험을 제안하면 해당 체크리스트 상태가 실제로 `MISSING`인지 확인한다.
체크리스트가 `COMPLIANT` 또는 `REVIEW`이면 LLM 누락 결과를 최종 위험 후보로
받아들이지 않는다.

최종 분석 흐름은 다음과 같다.

```text
PDF 텍스트 추출
→ 조항 단위 분리
→ 제목 동의어 및 시간 범위 인식
→ 명시적·간접적 체크리스트 근거 판정
→ 위험 규칙 판정
→ LLM 결과와 규칙 결과 상호 검증
→ 체크리스트와 누락 결과 충돌 검사
→ 중복·모순 결과 제거
→ 검증된 위험조항으로 점수 재계산
```

### 5. 회귀 테스트

`ai/tests/test_analyzer.py`에 다음 실제 문서 형태의 사례를 추가했다.

```text
제4조 근무시간
월요일~금요일 09:00~18:00 (휴게 12:00~13:00)
```

테스트는 다음을 검증한다.

- `근무시간` 제목을 근로시간 조항으로 인정하는지
- `09:00~18:00` 시간 범위를 근거로 인식하는지
- 근로시간 체크리스트가 `COMPLIANT`인지
- 휴일 체크리스트가 `MISSING`이 아닌 `REVIEW`인지
- `MISSING_WORK_HOURS`가 제거되는지
- `MISSING_HOLIDAY`가 제거되는지
- 검토 필요가 위험 점수가 아닌 별도 건수로 계산되는지

`ai/tests/test_agent.py`에는 LLM이 `MISSING_HOLIDAY`를 다시 생성해도 체크리스트가
`REVIEW`이면 해당 결과를 거부하는 회귀 테스트를 추가했다.

### 6. 검증 결과

실제 문제 PDF를 수정된 규칙으로 다시 분석한 결과는 다음과 같았다.

```text
WAGE: COMPLIANT

HOLIDAY: REVIEW
ANNUAL_LEAVE: COMPLIANT

MISSING_WORK_HOURS: 없음
MISSING_HOLIDAY: 없음

```

전체 AI 회귀 테스트는 `51 passed`로 완료되었다.

### 7. 배운 점

- 법률 문서의 필수 항목 판정은 특정 표준 용어 하나가 아니라 실무에서 사용하는
  동의어까지 포함해야 한다.
- `09:00~18:00` 같은 구조화된 값은 일반 키워드보다 강한 의미 근거로 평가해야 한다.
- 간접 근거가 있는 경우 `정상`과 `누락` 사이의 `검토 필요` 상태가 필요하다.
- 체크리스트, 위험규칙, LLM, RAG 결과는 독립적으로 생성한 뒤 단순 병합하면 안 된다.
- 최종 리포트 전에 근거 중복, 체크리스트 충돌, 누락 여부, 법령 연결을 다시 검증해야 한다.
- 실제 오류 PDF를 회귀 사례로 고정해야 이후 규칙이나 모델 변경으로 같은 문제가
  재발하는 것을 막을 수 있다.

## 소셜 로그인 티켓 교환 중 `LazyInitializationException`이 발생한 문제

### 1. 증상

Google 로그인과 OAuth 인증 화면은 정상적으로 통과했지만 LAWZIC으로 돌아온 뒤 로그인이
완료되지 않고 서버 처리 오류가 표시되었다.

백엔드에는 수백 줄의 Spring Security 필터 스택 트레이스가 출력됐지만 실제 원인을
나타내는 핵심 예외는 다음 한 줄이었다.

```text
org.hibernate.LazyInitializationException:
could not initialize proxy [com.lawzic.api.user.User#1] - no Session
```

실패 위치는 다음과 같았다.

```text
OAuthLoginService.exchange()
→ AuthController.exchangeOAuthTicket()
→ AuthController.authResponse()
→ User.getEmail()
```

### 2. 원인 분석

이 오류는 Google Client ID, Client Secret, Redirect URI 문제가 아니었다. Google 인증은
이미 성공했고, LAWZIC 백엔드가 일회용 OAuth 티켓을 교환하는 마지막 단계에서 실패했다.

`OAuthLoginTicket`의 사용자 연관관계는 지연 로딩으로 설정되어 있다.

```java
@ManyToOne(fetch = FetchType.LAZY)
private User user;
```

기존 `OAuthLoginService.exchange()`는 트랜잭션 안에서 티켓을 조회한 뒤 연관된 `User`
엔티티를 컨트롤러에 그대로 반환했다.

```text
OAuth 티켓과 User 프록시 조회
→ OAuthLoginService 트랜잭션 종료
→ Hibernate 세션 종료
→ AuthController에서 user.getEmail() 호출
→ 프록시 초기화에 필요한 세션이 없어 예외 발생
```

테스트용 H2나 일부 코드 경로에서는 엔티티가 이미 초기화되어 우연히 문제가 드러나지
않을 수 있다. MariaDB에서 실제 OAuth 티켓을 다시 조회하는 흐름에서는 `User`가 프록시
상태로 반환되어 트랜잭션 경계 문제가 명확하게 드러났다.

### 3. 거대한 스택 트레이스에서 원인을 찾은 방법

Spring Security 요청은 다수의 필터를 통과하므로 예외가 발생하면 인증·세션·CORS·JWT
필터 호출 내역이 길게 출력된다. 필터 목록 전체를 각각의 오류로 해석하지 않고 다음
순서로 확인했다.

1. 가장 먼저 출력된 예외 클래스 확인
2. 첫 번째 애플리케이션 패키지 `com.lawzic` 위치 확인
3. 해당 메서드에서 접근한 엔티티와 트랜잭션 경계 확인
4. 가장 안쪽 원인과 실제 SQL·OAuth 단계 구분

이번 로그의 첫 번째 애플리케이션 위치는 다음과 같았다.

```text
com.lawzic.api.user.User.getEmail()
com.lawzic.api.auth.AuthController.authResponse(AuthController.java:144)
```

따라서 OAuth 제공자 인증 실패가 아니라 인증 완료 후 사용자 응답과 JWT를 만드는
단계의 JPA 지연 로딩 문제로 범위를 좁힐 수 있었다.

### 4. 피한 임시 해결책

다음 방법은 당장 예외를 숨길 수 있지만 적용하지 않았다.

#### `spring.jpa.open-in-view=true`

웹 응답이 끝날 때까지 영속성 컨텍스트를 열어두면 컨트롤러에서도 지연 로딩이
가능해진다. 하지만 웹 계층에서 예측하지 못한 SQL이 실행되고 엔티티와 API의 경계가
불명확해진다. LAWZIC은 이미 `open-in-view: false` 정책을 사용하므로 유지했다.

#### 모든 연관관계를 `EAGER`로 변경

소셜 로그인 한 곳의 문제를 해결하기 위해 사용자 연관관계를 전부 즉시 로딩하면 다른
조회에서도 불필요한 데이터와 SQL이 증가한다.

#### 컨트롤러에 트랜잭션 추가

컨트롤러까지 DB 세션을 유지하면 서비스 계층의 트랜잭션 책임이 웹 계층으로 퍼진다.

### 5. 해결 방법

OAuth 서비스가 JPA `User` 엔티티를 직접 반환하지 않고, 트랜잭션 안에서 필요한 값을
읽어 불변 값 객체로 변환하도록 변경했다.

```java
public record AuthenticatedUser(
    Long id,
    String email,
    String name
) {
    static AuthenticatedUser from(User user) {
        return new AuthenticatedUser(
            user.getId(),
            user.getEmail(),
            user.getName()
        );
    }
}
```

수정된 처리 흐름은 다음과 같다.

```text
OAuthLoginService 트랜잭션 시작
→ 티켓 및 User 프록시 조회
→ 트랜잭션 내부에서 ID·이메일·이름 접근
→ AuthenticatedUser 값 객체 생성
→ 티켓 사용 시각 저장
→ 트랜잭션 종료
→ AuthController가 값 객체로 JWT와 사용자 응답 생성
```

다음 세 경로에 동일한 정책을 적용했다.

- 기존 소셜 계정의 OAuth 티켓 교환
- 일반 계정과 소셜 계정 연결
- 신규 소셜 회원가입 완료

컨트롤러는 더 이상 OAuth 서비스에서 반환된 JPA 엔티티나 Hibernate 프록시에
접근하지 않는다.

### 6. 회귀 테스트

`OAuthLoginServiceTests`에 티켓에 연결된 사용자로부터 세션 독립적인
`AuthenticatedUser`가 만들어지는 사례를 추가했다.

테스트는 다음 내용을 검증한다.

- 사용자 ID가 값 객체에 복사되는지
- 이메일과 이름이 값 객체에 복사되는지
- OAuth 티켓이 사용 처리되는지
- 소셜 회원가입 시 null이 아닌 내부 비밀번호 해시가 저장되는지
- 신규 가입, 기존 계정 연결, 기존 소셜 계정 교환이 같은 반환 정책을 사용하는지

수정 후 Maven 백엔드 전체 테스트가 성공적으로 완료되었다.

### 7. 운영 시 처리

Java 코드 변경이므로 실행 중인 백엔드를 재시작해야 한다.

```powershell
cd "C:\Users\human-21\Documents\Final Project\backend"
..\tools\apache-maven-3.9.9\bin\mvn.cmd spring-boot:run
```

실패한 OAuth 티켓은 오류 발생 전에 사용 처리됐을 수 있다. 사용자가 Google 로그인
버튼을 다시 누르면 새로운 일회용 티켓이 생성되므로 사용자 계정이나 소셜 연결 정보를
직접 삭제할 필요는 없다.

### 8. 배운 점

- OAuth 리디렉션 성공 이후의 오류를 OAuth 제공자 설정 오류로 단정하면 안 된다.
- JPA 엔티티를 서비스 트랜잭션 밖으로 반환하면 지연 로딩 프록시 문제가 발생할 수 있다.
- `open-in-view`나 전역 `EAGER`는 계층 경계 문제를 숨길 뿐 근본 해결이 아니다.
- 인증 응답과 JWT 생성에는 엔티티가 아니라 필요한 필드만 담은 불변 값 객체를 사용해야 한다.
- 긴 Spring Security 스택 트레이스에서는 필터 이름보다 최초 예외와 첫 애플리케이션
  코드 위치를 먼저 확인해야 한다.

## 수습기간 최저임금 질문에 연장·야간·휴일근로를 답변한 문제

### 1. 증상

노동법 AI 상담에서 다음과 같이 질문했다.

```text
수습기간에는 최저임금보다 적게 지급할 수 있나요?
```

하지만 답변에는 수습기간이나 최저임금이 아니라 이전 상담 주제였던 연장근로,
야간근로, 휴일근로와 가산수당 내용이 표시됐다. 답변에 연결된 법령도
근로기준법 제50조·제53조·제56조처럼 현재 질문과 관련 없는 근거였다.

이는 단순한 문장 표현 오류가 아니라 검색된 법령과 현재 질문이 일치하지 않은
RAG 검색 오류였다.

### 2. 재현 과정

다음과 같이 서로 다른 주제를 연속해서 질문하면 문제를 재현할 수 있었다.

```text
이전 질문: 연장근로는 일주일에 몇 시간까지 가능한가요?
현재 질문: 수습기간에는 최저임금보다 적게 지급할 수 있나요?
```

기존 검색 쿼리는 최근 사용자 질문 두 개와 현재 질문을 항상 하나로 합쳤다.

```text
연장근로는 일주일에 몇 시간까지 가능한가요?
+ 수습기간에는 최저임금보다 적게 지급할 수 있나요?
```

결합된 검색어로 벡터 검색과 주제 규칙을 실행하면 데이터가 이미 충분했던
연장근로 법령의 점수가 높아졌다. 그 결과 현재 질문보다 과거 질문을 설명하는
법령이 최종 답변에 사용됐다.

### 3. 근본 원인

#### 이전 대화를 무조건 검색어에 포함

후속 질문인지 새로운 질문인지 구분하지 않고 이전 질문을 항상 결합했다.
대화 문맥을 유지하려는 기능이 오히려 서로 다른 법률 주제를 오염시켰다.

```text
명확한 신규 질문
→ 이전 질문까지 결합
→ 여러 주제의 법령 ID가 동시에 허용됨
→ 검색 점수가 높은 과거 주제의 법령 선택
```

#### 수습기간 최저임금 법령 데이터 누락

기존 법령 RAG에는 임금 지급, 근로시간, 연장근로, 휴게시간 등의 근로기준법
조문은 있었지만 다음 핵심 근거가 없었다.

- 최저임금법 제5조
- 최저임금법 시행령 제3조

현재 질문과 정확히 일치하는 문서가 없으므로 검색기가 과거 질문의 연장근로
문서를 선택하기 쉬운 상태였다.

#### 회귀 데이터셋의 상담 주제 부족

기존 상담 회귀 데이터는 연장근로, 임금 공제, 휴게시간, 연차, 퇴직금과 해고
등을 검증했지만 수습기간과 최저임금 조합은 포함하지 않았다. 또한 서로 다른
주제를 연속해서 질문했을 때 현재 질문이 이전 질문과 분리되는지도 검증하지
않았다.

#### 검색 성공 여부만 확인하고 주제 전환을 검증하지 않음

검색 관련도 임계값과 인용 후처리는 있었지만, `현재 질문에서 식별한 주제`와
`최종 법령의 주제`가 동일한지 확인하는 테스트가 부족했다. 따라서 출처 형식은
정상이어도 출처 자체가 엉뚱할 수 있었다.

### 4. 해결 방법

#### 현재 질문을 우선하는 문맥 결합 정책

현재 질문만으로 법률 주제를 식별할 수 있으면 이전 대화를 검색어에 포함하지
않도록 변경했다.

```text
현재 질문에 수습 + 최저임금 표현 존재
→ 현재 질문만 검색
→ 이전 연장근로 질문 제외
```

`그럼 수당은?`, `그 경우 기간은?`처럼 현재 문장만으로 대상을 알 수 없는
실제 후속 질문에만 가장 최근 사용자 질문 한 건을 결합한다.

```python
if supported_evidence_ids(current_question):
    return current_question

if is_follow_up_expression(current_question):
    return previous_question + current_question

return current_question
```

이 정책으로 대화 문맥은 유지하면서 명확한 신규 주제의 검색 오염을 방지했다.

#### 최저임금 관련 법령 데이터 추가

공식 국가법령정보센터를 기준으로 다음 문서를 법령 RAG에 추가했다.

- 최저임금법 제5조: 수습 근로자 특례의 계약기간·적용기간·직종 조건
- 최저임금법 시행령 제3조: 적용 가능한 감액 비율

상담 답변은 다음 조건을 함께 설명하도록 근거를 구성했다.

```text
원칙: 최저임금 이상 지급
예외: 1년 이상 근로계약을 체결한 수습 근로자
기간: 수습 시작일부터 3개월 이내
범위: 시간급 최저임금의 90%
제외: 고시된 단순노무직
```

#### 질문 주제와 허용 법령 ID를 명시적으로 연결

`수습`, `수습기간`과 `최저임금`, `감액`, `90%` 등의 의미가 함께 나타나면
다음 법령만 검색 결과로 허용한다.

```text
minimum-wage-act-5
minimum-wage-enforcement-decree-3
```

벡터 유사도가 높더라도 허용된 주제의 법령 ID가 아니면 최종 근거에서 제거한다.

#### 검색용 메타데이터와 사용자용 법령 본문 분리

벡터 검색을 위해 문서에 결합했던 `관련어` 문자열이 RAG 대체 답변에 그대로
노출되는 문제도 함께 수정했다. 검색 문서와 원문 법령 텍스트를 별도로 저장하고,
사용자 답변에는 정제된 법령 본문만 전달한다.

### 5. 회귀 테스트

실제 오류 흐름을 상담 회귀 데이터에 추가했다.

```text
이전 질문: 연장근로는 일주일에 몇 시간까지 가능한가요?
현재 질문: 수습기간에는 최저임금보다 적게 지급할 수 있나요?
```

테스트는 다음 내용을 검증한다.

- 현재 검색어에 `연장근로`가 남아 있지 않은지
- 최저임금법 제5조가 검색되는지
- 최저임금법 시행령 제3조가 검색되는지
- 연장근로 관련 법령이 반환되지 않는지
- 관련도가 낮은 다른 법령이 제거되는지
- 답변에 표시된 출처가 실제 사용한 법령과 일치하는지

### 6. 검증 결과

수정된 실제 상담 API에 동일한 이전 대화와 질문을 전송한 결과는 다음과 같았다.

```text
반환 법령:
- 최저임금법 제5조
- 최저임금법 시행령 제3조

연장근로 법령: 없음
야간근로 법령: 없음
휴일근로 법령: 없음
근거 부족 상태: false
```

자동화 테스트 결과:

```text
상담 회귀 테스트: 15 passed
AI 전체 테스트: 54 passed
AI 서버 상태 확인: 정상
실제 상담 API 호출: 정상
```

### 7. 성과

- 명확한 신규 질문이 과거 상담 주제에 오염되는 문제를 차단했다.
- 관련 법령이 없는 상태에서 유사한 다른 법령을 억지로 연결하는 문제를 제거했다.
- 수습기간 최저임금 질문에 조건, 기간, 감액 범위와 적용 제외 대상을 함께
  안내할 수 있게 됐다.
- 답변 내용과 화면에 표시되는 법령 출처가 동일한 주제를 설명하도록 만들었다.
- 실제 장애 사례를 회귀 데이터로 고정해 이후 프롬프트, 임베딩 모델이나 검색
  로직을 변경해도 같은 오류를 자동으로 탐지할 수 있게 됐다.

### 8. 배운 점

- 대화형 RAG에서 이전 대화를 많이 넣는 것이 항상 문맥 이해를 높이지는 않는다.
- 후속 질문 판별 없이 전체 대화를 검색어에 결합하면 주제 전환 시 검색 오염이
  발생한다.
- 관련도 필터만으로는 데이터베이스에 정답 문서가 없는 문제를 해결할 수 없다.
- 법률 상담은 답변 문장의 자연스러움보다 질문, 검색 법령, 인용 출처의 주제
  일치 여부를 먼저 검증해야 한다.
- 실제 사용자 질문과 대화 순서를 회귀 데이터셋에 포함해야 운영 환경의 오류를
  재현하고 재발을 막을 수 있다.
